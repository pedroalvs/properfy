# Shared Package – Guidance for Claude Code

You are working inside **`packages/shared/`** of the Properfy monorepo.

This package is the **single source of truth** for types, enums, schemas and contracts shared between `apps/backend`, `apps/web` and `apps/pwa`. It ensures consistency across the entire stack.

---

## 1. Tech stack

- **Language:** TypeScript
- **Validation:** Zod (schemas that generate both runtime validation and TypeScript types)
- **Package manager:** pnpm (workspace package)
- **Build:** tsup (CJS + ESM + `.d.ts`). web, pwa and backend typecheck resolve `@properfy/shared` from `dist/`, so **build after every change** (`pnpm --filter @properfy/shared build`). Backend Vitest aliases the source (`apps/backend/vitest.config.ts`), so backend tests can pass while typecheck still sees the old `dist`.

## 5. Zod schemas

Schemas serve double duty: **runtime validation** (backend) and **TypeScript type inference** (all workspaces).

### Pattern

```typescript
import { z } from 'zod';

// Schema definition
export const createAppointmentSchema = z.object({
  branchId: z.string().uuid(),
  propertyId: z.string().uuid().optional(),
  serviceTypeId: z.string().uuid(),
  scheduledDate: z.string().date(),
  timeSlot: z.string(),
  contact: z.object({
    tenantName: z.string().min(1),
    primaryEmail: z.string().email().optional(),
    primaryPhone: z.string().optional(),
  }),
  keyRequired: z.boolean().default(false),
  notes: z.string().optional(),
});

// Type inference
export type CreateAppointmentInput = z.infer<typeof createAppointmentSchema>;
```

## 6. Status transition map

The valid transition map is defined here and used by the frontends (web, pwa) to decide which actions to offer. The backend authority is `TRANSITION_RULES` in `appointment-state-machine.ts` (actors, reason, done-check); keep both in sync.

```typescript
export const VALID_TRANSITIONS: Record<AppointmentStatus, AppointmentStatus[]> = {
  DRAFT: ['AWAITING_INSPECTOR', 'SCHEDULED', 'REJECTED', 'CANCELLED'],
  AWAITING_INSPECTOR: ['SCHEDULED', 'CANCELLED', 'REJECTED'],
  SCHEDULED: ['DONE', 'CANCELLED', 'REJECTED'],
  DONE: ['DRAFT', 'REJECTED'],
  CANCELLED: ['DRAFT'],
  REJECTED: ['DRAFT', 'AWAITING_INSPECTOR', 'CANCELLED'],
};
```

## 7. Naming conventions

- **TypeScript:** `camelCase` for variables/functions, `PascalCase` for types/interfaces/enums
- **Zod schemas:** `camelCase` with `Schema` suffix (e.g., `createAppointmentSchema`)
- **Enum constants:** `PascalCase` for the const object, `UPPER_SNAKE_CASE` for values
- **Files:** `kebab-case` (e.g., `appointment-status.ts`, `create-appointment.ts`)
- **Barrel exports:** every directory has an `index.ts`

## 10. Conventions for Claude Code

When you (Claude Code) work on the shared package:

1. **This is the single source of truth** – if a type, enum or schema exists here, do NOT duplicate it in any workspace.
2. **Add Zod schemas for all API contracts** – they generate both validation and types.
3. **Keep it lean** – only shared concerns belong here. Domain-specific logic stays in the backend.
4. **Every new enum or type** used by more than one workspace must go here.
5. **Barrel exports** – always update `index.ts` files.
6. **Test schemas** – every Zod schema needs validation tests.
7. **Naming matters** – use the conventions above consistently.
8. **Breaking changes affect all workspaces** – be careful with schema modifications.
9. **Entity definitions** live in `apps/backend/prisma/schema.prisma`; the API contract is `openapi.json` (generated — never hand-edit it or `src/api-types.ts`; run `pnpm generate:api`).
10. **Settings schemas live here:** per-agency fields in `tenantSettingsSchema` (`schemas/tenant.ts`, always optional), platform-wide keys in the `PLATFORM_SETTINGS_REGISTRY` (`schemas/platform-settings.ts`). Every key has a Zod schema, complete defaults that pass that schema, and a `section` display label, with tests; a feature adds configuration by appending one new key, never by repurposing an existing one. Example per-agency key: `mapWindowDays` (`z.number().int().min(1).max(90).optional()`) — the default map period window in days, with `MAP_WINDOW_DAYS_DEFAULT = 14` exported from the same module as the fallback when the key is absent or invalid (the schema is `.passthrough()`, so readers must revalidate, e.g. web `resolveMapWindowDays`).
11. **Dates:** civil dates and windows are agency wall-clock (`tenants.timezone`), except inspector day plans (`DayPlan`), which use the inspector's timezone; instants are UTC; convert only with the helpers in `utils/timezone-date.ts` and `utils/format-display-date.ts` (root `CLAUDE.md` §9, "Dates and timezones").

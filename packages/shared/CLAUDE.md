# Shared Package – Guidance for Claude Code

You are working inside **`packages/shared/`** of the Properfy monorepo.

This package is the **single source of truth** for types, enums, schemas and contracts shared between `apps/backend`, `apps/web` and `apps/pwa`. It ensures consistency across the entire stack.

---

## 1. Tech stack

- **Language:** TypeScript
- **Validation:** Zod (schemas that generate both runtime validation and TypeScript types)
- **Package manager:** pnpm (workspace package)
- **Build:** tsup (CJS + ESM + `.d.ts`). web, pwa and backend typecheck resolve `@properfy/shared` from `dist/`, so **build after every change** (`pnpm --filter @properfy/shared build`). Backend Vitest aliases the source (`apps/backend/vitest.config.ts`), so backend tests can pass while typecheck still sees the old `dist`.

## 5. Zod schemas

Schemas serve double duty: **runtime validation** (backend) and **TypeScript type inference** (all workspaces).

### Pattern

```typescript
import { z } from 'zod';

// Schema definition
export const createAppointmentSchema = z.object({
  branchId: z.string().uuid(),
  propertyId: z.string().uuid().optional(),
  serviceTypeId: z.string().uuid(),
  scheduledDate: z.string().date(),
  timeSlot: z.string(),
  contact: z.object({
    tenantName: z.string().min(1),
    primaryEmail: z.string().email().optional(),
    primaryPhone: z.string().optional(),
  }),
  keyRequired: z.boolean().default(false),
  notes: z.string().optional(),
});

// Type inference
export type CreateAppointmentInput = z.infer<typeof createAppointmentSchema>;
```

### Shared schemas

- **Pagination:** `paginationSchema` (`page`, `pageSize`, `sortBy`, `sortOrder`); response meta: `paginationMetaSchema` (`schemas/responses.ts`)
- **Error:** the `{ error: { code, message, details } }` envelope is parsed by `utils/api-error.ts` (no exported Zod schema)
- **Status transition:** `statusTransitionSchema` with `targetStatus`, `reason`
- **Geocoding (X02-1):** `branchAddressSchema` (`schemas/address.ts`) has **no** `latitude`/`longitude` — branch coordinates come only from permanent-mode geocoding on the backend, and it stays a plain `z.object` (no top-level `.transform/.refine/.superRefine` etc.) so F01 can `.extend(...)` it. `geocodeVerificationSchema` (`schemas/import.ts`) `found` variant carries an optional `mode: z.literal('permanent')`; a `found` without a mode is a pre-deploy preview and is re-geocoded on commit.
- **Inspector field events (F03-2):** `enums/field-events.ts` adds `InspectorFieldEventType` (`CANT_DO`/`LATE_NOTICE`), `FieldIssueReason`/`LateNoticeReason` + label maps, `FIELD_ISSUE_NOTE_REQUIRED_REASONS`, `LATE_NOTICE_MINUTES_OPTIONS` (alongside the F03-1 `GeofenceMode`). `schemas/field-events.ts` holds `cantDoRequestSchema`/`cantDoResponseSchema`, `lateNoticeRequestSchema`/`lateNoticeResponseSchema` (response carries `referenceAt`/`referenceSource`/`estimatedArrivalAt`), `inspectorIssueSchema`, `inspectorLastFieldIssueSchema`, `fieldEventItemSchema`, `executionSummarySchema` (lat/lng declared **optional** so the backend can omit them for CL roles), `appointmentFieldActivityResponseSchema`. `appointmentResponseSchema.inspectorIssue` and `inspectorAppointmentDetailResponseSchema.lastFieldIssue` are declared (nullable/optional) in `schemas/responses.ts` (undeclared fields are stripped). `reason-codes.ts` adds `RejectionReasonCode.INSPECTOR_UNABLE` + `SYSTEM_ONLY_REJECTION_CODES`; `constants/transition-sources.ts` has `TRANSITION_SOURCE_INSPECTOR_CANT_DO`; `constants/inspector-notices.ts` has `COMPLETION_REMINDER_DEDUPE_PREFIX` + `buildCompletionReminderDedupeKey`. `notification-templates.ts` registers the `INSPECTOR_UNABLE_ALERT` platform code (8 places) and adds the `rejectedByInspector`/`fieldIssueReason`/`fieldIssueNote` variables.
- **Inspector base address (F01-1):** `inspectorBaseAddressSchema` + `AU_STATES` (`schemas/address.ts`) is **derived** from `branchAddressSchema` with trim, an AU state enum, a 4-digit postcode and `country: 'AU'`; Zod strip drops any client `latitude/longitude`. `createInspectorSchema.address` is **required**; `updateInspectorSchema.address`/`inspectorSelfUpdateSchema.address` are `.optional()` and **not** `.nullable()` (so `address:null` is a 400 — the base is never removable). `inspectorAppStateSchema` is the app-state heartbeat body (`displayMode`/`pushPermission`/`appVersion`, plus F04-2 `onboardingCompleted: z.literal(true).optional()` — write-once, `false` is rejected). `listInspectorsQuerySchema.missingBaseAddress` uses `booleanQueryParam()` (never `z.coerce.boolean`). `inspectorResponseSchema` carries optional `baseLat/baseLng/baseGeocodedAt/baseGeocodeFailed`, `appInstalledAt/appLastSeenAt/pushEnabled/appVersion` and F04-2 `onboardingCompletedAt` (visible to AM/OP + the inspector, stripped for CL).
- **Inspector notices (F02-1):** `schemas/inspector-notice.ts` (publish/audience/summary/detail/my-notice/push-subscription schemas) + `constants/inspector-notices.ts` (`SYSTEM_INSPECTOR_NOTICE_TYPES`, `SYSTEM_NOTICE_CRITICALITY`/`isCriticalSystemNoticeType`, `INSPECTOR_NOTICE_TARGET_PATTERNS` + `isAllowedInspectorNoticeTargetPath` — the deep-link allowlist shared with the PWA service worker, `resolveInspectorNoticeTargetPath`, `getInspectorNoticeDeliverExpireMinutes`, `buildInspectorNoticeSmsMessage`, `isAllowedPushEndpoint` — the push-service host allowlist that `pushSubscriptionSchema.endpoint` and `WebPushSender` enforce as an SSRF guard, since delivery makes a server-side request to that URL). The SMS fallback template `INSPECTOR_NOTICE_SMS` is registered in `constants/notification-templates.ts` (platform-only, TRANSACTIONAL, target `INSPECTOR`, `{{{message}}}` triple-stash) — **not** added to `NotificationChannel` (stays `EMAIL | SMS`; no `PUSH`).
- **Route planning (F04-1):** `route-planning/` is a **pure, I/O-free** optimizer (no Node imports — it is bundled into the PWA for local reorder recompute). It is exported both from the main barrel and via the **`@properfy/shared/route-planning` subpath** (a second `tsup` entry + `exports["./route-planning"]`, added by TASK-F04-4) so the PWA reorder can import `evaluateSequence`/`RouteOrderMismatchError` without dragging the optimizer into the eager bundle through the app-wide barrel. Contents: `optimizeRoute` (exact DFS ≤ 8 stops, nearest-feasible + 2-opt above), `evaluateSequence` (hard windows + forward slack, optional `legTravelS`/`earliestDepartureS`), `insertIntoOrder`, `compareEvaluations`/`toWeightTenths`, `haversineMeters` (R = 6371008.8), `selectMatrixProfile` (≤10 `driving-traffic`, 11–25 `driving`, ≥26 null), plus the `OptimizerStop`/`OptimizerInput`/`SequenceEvaluation`/`RouteWeights` types and `RouteOrderMismatchError`. `costTenths` is weighted seconds (÷10 for display). The backend `PlanRouteService` and the PWA reorder both call it. **Day-plan Plan B (072):** `schemas/day-plan.ts` adds `previewDayPlanOrderRequestSchema` (same shape as `saveDayPlanOrderRequestSchema`) + `previewDayPlanOrderResponseSchema` (`etaSource: 'MATRIX'`, evaluated stops/totals) for the new INSP `POST /v1/inspector/day-plans/:date/order/preview`. `dayPlanResponseSchema.geometry` and `.routingInput` are unchanged in shape but are now populated **on demand** by the backend (never from stored Mapbox results); `routingInput`/`dayPlanRoutingInputSchema`/`toOptimizerInput`/`buildLegOverrides` are intentionally kept until PR-C (after the PWA moves to the preview endpoint). **Service-type duration (F04-1 / F04-5):** `constants/service-type.ts` (`SERVICE_TYPE_DURATION_{MIN,MAX,DEFAULT}_MINUTES` = 5/480/45); `createServiceTypeSchema.defaultDurationMinutes` is **required** (F04-5 removed the transitional `.default(45)`; the web form now collects it and the `POST /v1/service-types` body validation rejects a missing value), `updateServiceTypeSchema` optional (same 5–480 bounds), `serviceTypeResponseSchema` `z.number().int()`. The DB column keeps `DEFAULT 45` for direct inserts/seeds; `SERVICE_TYPE_DURATION_DEFAULT_MINUTES` stays exported for those.
- **Execution density (F09-1):** `schemas/execution-density.ts` holds `executionDensityQuerySchema` (`fromDate`/`toDate` `civilDateSchema`, `toDate >= fromDate`, inclusive period ≤ 366 days, optional uuid `tenantId`/`inspectorId`) and `executionDensityResponseSchema` (`cells[]` of `{lat,lng,count≥1}`, `minCellCount`, `totalExecutions`, `cellCount`, `excludedWithoutCoordinates`, `truncated`, `gridSizeDegrees` as the literal `EXECUTION_DENSITY_GRID_DEGREES`). Constants: `EXECUTION_DENSITY_GRID_SCALE` (1000), `EXECUTION_DENSITY_GRID_DEGREES` (0.001), `MAX_EXECUTION_DENSITY_PERIOD_DAYS` (366), `MAX_EXECUTION_DENSITY_CELLS` (5000), `MIN_CELL_COUNT_CL` (3), `MIN_CELL_COUNT_GLOBAL` (1), `EXECUTION_DENSITY_PRESET_DAYS` (`[7,30,90]`). Pure helper `isExecutionDensityPreset(range, today)` (used by the backend use case and the F09-2 web control) — true when `range` is exactly one preset look-back ending `today`. The web does **not** import `MIN_CELL_COUNT_CL`; it reads `minCellCount` from the response. New role-matrix action `map.execution_density` (`permissions/role-matrix.ts`: `roles: ['AM','OP','CL_ADMIN','CL_USER']`, no condition; the `inspectorId` filter is AM/OP-only, enforced in the backend use case).

## 7. Naming conventions

- **TypeScript:** `camelCase` for variables/functions, `PascalCase` for types/interfaces/enums
- **Zod schemas:** `camelCase` with `Schema` suffix (e.g., `createAppointmentSchema`)
- **Enum constants:** `PascalCase` for the const object, `UPPER_SNAKE_CASE` for values
- **Files:** `kebab-case` (e.g., `appointment-status.ts`, `create-appointment.ts`)
- **Barrel exports:** every directory has an `index.ts`

## 10. Conventions for Claude Code

When you (Claude Code) work on the shared package:

1. **This is the single source of truth** – if a type, enum or schema exists here, do NOT duplicate it in any workspace.
2. **Add Zod schemas for all API contracts** – they generate both validation and types.
3. **Keep it lean** – only shared concerns belong here. Domain-specific logic stays in the backend.
4. **Every new enum or type** used by more than one workspace must go here.
5. **Barrel exports** – always update `index.ts` files.
6. **Test schemas** – every Zod schema needs validation tests.
7. **Naming matters** – use the conventions above consistently.
8. **Breaking changes affect all workspaces** – be careful with schema modifications.
9. **Entity definitions** live in `apps/backend/prisma/schema.prisma`; the API contract is `openapi.json` (generated — never hand-edit it or `src/api-types.ts`; run `pnpm generate:api`).
10. **Settings schemas live here:** per-agency fields in `tenantSettingsSchema` (`schemas/tenant.ts`, always optional), platform-wide keys in the `PLATFORM_SETTINGS_REGISTRY` (`schemas/platform-settings.ts`). Every key has a Zod schema, complete defaults that pass that schema, and a `section` display label, with tests; a feature adds configuration by appending one new key, never by repurposing an existing one. Example per-agency key: `mapWindowDays` (`z.number().int().min(1).max(90).optional()`) — the default map period window in days, with `MAP_WINDOW_DAYS_DEFAULT = 14` exported from the same module as the fallback when the key is absent or invalid (the schema is `.passthrough()`, so readers must revalidate, e.g. web `resolveMapWindowDays`).
11. **Dates:** civil dates and windows are agency wall-clock (`tenants.timezone`), except inspector day plans (`DayPlan`), which use the inspector's timezone; instants are UTC; convert only with the helpers in `utils/timezone-date.ts` and `utils/format-display-date.ts` (root `CLAUDE.md` §9, "Dates and timezones").

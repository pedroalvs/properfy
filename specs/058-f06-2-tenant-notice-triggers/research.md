## D-R1. Consent email case-insensitivity fix (the handed-off issue)

**Problem.** `SendNotificationUseCase.isBlockedByConsent` (`send-notification.use-case.ts:676`) looks up `consentRepo.findByScope({ recipient: notification.recipient, … })` with the **raw** recipient, and `PrismaNotificationConsentRepository.findByScope` matches `recipient` with exact case-sensitive equality. F06-1's `RecordConsentOptOutUseCase.normalizeRecipient` deliberately stores email **trim-only** (not lowercased) with a comment that full case-insensitivity "is left to F06-2". Result: an opt-out recorded for `Ana@Example.com` does **not** block a send whose snapshot recipient is `ana@example.com` — a silent non-block once F06 starts sending.

**Decision.** Canonicalize **email** recipients to lowercase at the **consent-repository choke point** — both the stored value on `upsert` and every consent-table lookup (`findByScope`, the `upsert` findFirst, `listByRecipient`). Phone (`SMS`) is left unchanged (already E.164-canonical). Also lowercase email in `RecordConsentOptOutUseCase.normalizeRecipient` (so `ConsentRecordOutput.recipient` matches the stored value) and fix its now-false "do NOT lowercase" comment and the class JSDoc.

**Rationale.** Email is case-insensitive by identity convention; lowercasing at the single repo choke point fixes the read path (`isBlockedByConsent`), the write path (`RecordConsentOptOutUseCase` and `OverrideConsentUseCase` both go through `upsert`), and the operator lookup (`listByRecipient`) in one place, with **no migration and no backfill**. It is deterministic and `_`-safe, unlike Prisma `mode:'insensitive'` (which compiles to `ILIKE`, treating `_`/`%` in an email as wildcards). The only pre-F06-1 consent writer is `OverrideConsentUseCase`, which updates an existing row **by id**; the operator opt-out *creator* is new in F06-1, so there are effectively **no legacy OPERATIONAL email opt-out rows** to retro-match — making write+read lowercasing fully correct, not just minimal. A documented caveat: any pre-existing non-lowercase OPERATIONAL email consent row is not retro-matched; re-recording through the (now-canonicalizing) operator UI fixes it. `countSkippedForRecipient` queries the `notifications` table (raw as-sent recipients) and is left untouched.

**Alternatives rejected.** (a) Prisma `mode:'insensitive'` on `findByScope` — unsafe for emails containing `_`. (b) `lower()` raw SQL in the repo — covers legacy but adds raw queries to several methods; unnecessary given no legacy rows exist. (c) Backfill + store-lowercased (task Option 2) — needs a data script; "no migration" scope and no legacy rows make it overkill.

**Test.** A consent test records an EMAIL opt-out for a mixed-case address and asserts `isBlockedByConsent` (or the pipeline) blocks a differently-cased send of the same address; it fails on `develop` before the fix. Phone matching is asserted unchanged.

## D-R2. SMS consent recipient must be E.164 in the notifier

**Finding.** `AppointmentContactEntity.effectivePhone` is the raw `snapshotPhone` (not guaranteed E.164). The send pipeline only E.164-normalizes at *send* time, but `isBlockedByConsent` matches `notification.recipient` **before** that, while the opt-out stores E.164 — so a phone opt-out can silently fail to block too.

**Decision.** In the notifier, set the SMS notification `recipient = toE164Au(effectivePhone) ?? effectivePhone` (shared helper). This makes the stored recipient match the E.164 opt-out and the pipeline send. Email recipient stays `effectiveEmail` raw (the repo fix handles casing). No separate phone opt-out normalization is needed beyond what F06-1 already does on write.

## D-R4. Payload metadata typing (`payloadJson` is `Record<string, string>`)

`CreateNotificationInput.payloadJson` is `Record<string, string>` and `BuildNotificationPayloadService.build()` returns strings. The extra metadata keys the task wants on each row — `etaBandFromAt`, `serviceStartAt` (both already ISO strings), `planVersion`, `approximate` — must therefore be **stringified** (`String(planVersion)`, `String(approximate)`) when added to `payloadJson`. The TDD tests assert the stored string forms (e.g. `payloadJson.planVersion === String(fresh.planVersion)`, `payloadJson.etaBandFromAt === band.from.toISOString()`); the structured `tenant_eta.notice_created` **log** carries the native-typed values (`planVersion: number`, `approximate: boolean`). None of the four keys is a template variable or in `ALLOWED_VARIABLES`, and none is in `SENSITIVE_PAYLOAD_KEYS`, so they survive the post-send scrub. `serviceStartAt` comes from the stop's `EtaPlanStop.serviceStartAt`; `planVersion` from the fresh read; `approximate` from `plan.approximate` (snapshot).
